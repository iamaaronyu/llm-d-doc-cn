# KV 缓存管理

键值（KV）缓存管理是 llm-d 高性能 LLM 服务的基础。通过高效地追踪、保留和复用 KV 缓存——即 LLM 推理过程中生成的中间状态——llm-d 显著降低了延迟，并提升了推理资源池的整体吞吐量。

llm-d 中的 KV 缓存管理生态由三大核心架构支柱组成。通过组合这些层，llm-d 可以让推理资源池的“有效缓存容量”远超物理 HBM 的限制，即使在繁重、多样的工作负载下也能保持高命中率。三大支柱如下：

## 前缀缓存感知路由 {#prefix-cache-aware-routing}

由 **llm-d 路由器**（通过其 **EPP** 组件）管理的“智能”层，它利用索引为每个传入请求确定最优的模型服务器 Pod。其目标是把请求路由到已经包含该请求提示词前缀相关 KV 缓存的副本，从而最大化“缓存命中”。

请参阅**[前缀缓存感知路由](prefix-cache-aware-routing.md)**，深入了解 llm-d 路由器提供的两种不同路由实现：近似（基于启发式）实现和精确（基于事件）实现。

## KV 缓存索引 {#kv-cache-indexing}

“可观测性”层，持续监控资源池的状态，准确知道缓存了什么、缓存在哪里（包括卸载层以及所有活跃的模型服务器）。它消费来自 vLLM 等引擎的高频事件，以追踪各个 token 块的移动和淘汰。

请参阅**[KV 缓存索引器](kv-indexer.md)**，深入了解索引器如何处理 `KVEvents`，并为精确路由决策提供唯一事实来源。

## KV 卸载 {#kv-offloading}

“容量”层，把缓存扩展到加速器（GPU/TPU）有限的高带宽内存（HBM）之外。它使模型服务器能够把缓存条目“溢出”或卸载到 CPU 内存或本地 SSD，从而为 KV 缓存构建分层存储体系。

**请参阅 [KV 卸载器](kv-offloader.md)**，深入了解多级存储 API 的设计及其与推理引擎的集成。

## P2P 共享 {#p2p-sharing}

“共享”层，把三大支柱组合成集群级的缓存：索引知道哪个对等节点持有请求的前缀，路由器在请求上标明该来源，模型服务器则通过 NIXL 直接从对等节点的 CPU 卸载层拉取这些块，而不是重新计算。源 Pod 的 GPU 完全不会被触及，因此响应一次拉取不会占用它的 prefill 能力；普通的查找未命中或部分匹配会退化为正常的重新计算，而不会导致请求失败（已承诺但未交付的块是一个已记录的局限——参见指南）。

**请参阅[启用 P2P 前缀缓存共享](../../../well-lit-paths/foundations/enable-p2p-prefix-cache-sharing.md)**了解其机制和使用时机，并参阅 **[P2P KV 缓存共享指南](https://github.com/llm-d/llm-d/tree/v0.10.0/guides/p2p-kv-cache-sharing)**了解部署和基准测试。
