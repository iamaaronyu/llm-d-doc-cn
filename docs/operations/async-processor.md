# llm-d 异步处理器运维指南

本指南介绍[异步处理器](https://github.com/llm-d/llm-d-async)的运维最佳实践、扩缩行为以及容器规格建议。

异步处理器是一个**轻量级分发代理**，而不是推理引擎。它从消息队列（Redis 或 GCP Pub/Sub）中拉取请求，让请求通过分发门控，然后通过 HTTP 转发给 llm-d 路由器。由于繁重的工作（token 生成）发生在模型服务器上，处理器几乎完全是 **I/O 密集型**的：每个工作线程绝大部分时间都阻塞在对路由器的长时间 HTTP 调用上。这决定了下面的每一项规格决策——容器很小，约束在于并发度和载荷缓冲，而不是计算。

:::note
[第 2 节](#2-choosing-concurrency-the-most-important-sizing-decision)中关于**并发度**的建议有该节中的实测参数扫描作为支撑。[第 3 节](#3-container-resource-sizing)中的 **CPU/内存**数据是根据架构推导出的起点——请针对你自己的工作负载进行验证，并在有实测数据时优先采用自己的测量结果。
:::

## 1. 吞吐模型 {#1-throughput-model}

在确定规格之前，需要先理解处理器如何扩展。

- **工作线程是进行中并发的基本单位。**每个工作线程拉取一个请求，分发出去，然后阻塞直到路由器返回结果（或截止时间到期）。处理器同时能有的进行中请求总数，等于各工作线程数之和。
- **瓶颈在下游，而不在处理器。**分发速率最终受推理服务器容量和[分发门控](../architecture/advanced/batch/async-processor.md#dispatch-gates)限制，而不是受处理器的 CPU 限制。增加超出推理资源池承受能力的工作线程，只会增大队列积压和内存占用，而不会提升吞吐。
- **扩展是水平且无状态的。**处理器是基于拉取的消费者。针对同一个队列运行 N 个副本，就会成倍增加有效并发：`进行中总数 = 副本数 × 每副本工作线程数`。队列后端会把消息分发给所有消费者，因此不需要 leader 选举或协调。

### 并发配置 {#concurrency-configuration}

在 Helm Chart 中，并发度由 `ap.concurrency`（默认 `64`）控制；当不同的队列/主题需要独立的并行度时，也可以通过 `ap.workerPools` 按池控制：

```yaml
ap:
  concurrency: 64       # 全局工作线程数（默认）
  # 或者，按队列控制：
  workerPools:
    - id: "high-priority"
      workers: 16
    - id: "bulk"
      workers: 8
```

设置了 `workerPools` 时，每个池的 `workers` 值会覆盖该池的全局 `concurrency`。副本的进行中总并发等于所有池工作线程数之和。

## 2. 选择并发度（最重要的规格决策） {#2-choosing-concurrency-the-most-important-sizing-decision}

并发度是影响最大的单一调节项。默认值 `64` 是一个合理的起点——足以让一个中等规模的资源池保持忙碌——但它**并不**自动适合你的场景：单块大型 GPU 在此之上仍有余量，而高吞吐或长输出的工作负载需要多得多的并发。规格规则就是 Little 定律：

```
所需工作线程数 ≈ 目标吞吐量（请求/秒）× 平均请求延迟（秒）
```

由于 LLM 请求很慢（端到端需要数秒到数分钟），延迟这个乘数很大：如果平均请求耗时 2 秒，`concurrency: 64` 会把吞吐上限限制在 `64 / 2 = 32 请求/秒`，无论路由器后面有多少 GPU（旧的默认值 `8` 只能达到 `4 请求/秒`）。

### 实测参数扫描 {#measured-sweep}

我们针对一套线上 llm-d 技术栈运行了闭环参数扫描（每个工作线程在请求的整个持续期间持有一个进行中请求——这正是异步处理器工作线程的行为）：**vLLM 上的 Llama-3.1-8B（`--max-num-seq 1024`），单块 H100-80GB**，输出约 256 个 token，经推理网关 + EPP 分发。吞吐量和 vLLM KV 缓存利用率随并发度的变化：

| 并发度 | 吞吐量（请求/秒） | 平均延迟（秒） | GPU KV 占用 | 备注 |
| :--- | :--- | :--- | :--- | :--- |
| 8 | 4.2 | 1.9 | <1% | 旧默认值——GPU 基本空闲 |
| 32 | 14.7 | 2.2 | 3% | |
| **64（默认）** | **24.1** | 2.6 | 5% | 当前默认值 |
| 128 | 35.8 | 3.6 | 12% | 接近饱和 |
| 192 | 40.4 | 4.7 | 16% | **拐点——吞吐/延迟最佳** |
| 256 | 44.3 | 5.8 | 20% | 越过拐点，延迟上升 |
| 512 | 61.4 | 9.7 | 51% | 不稳定：重复运行中出现错误 |

要点：

- **默认值 `64` 能达到峰值吞吐的约 60%。**在 `concurrency: 64` 下，这块 H100 可持续约 24 请求/秒（KV 5%）——一个不错的起点，但距离拐点处的约 40 请求/秒仍有差距。旧默认值 `8` 只能达到约 4 请求/秒（KV <1%），大约比拐点**低 10 倍**。
- **该后端的拐点约在 128–192——大约是默认值 `64` 的 2–3 倍。**越过拐点后，延迟上升得比吞吐快（从 256 到 512，延迟翻倍，吞吐只多约 40%）。
- **Little 定律完全成立。**在每个稳定点上，进行中请求数（`吞吐 × 延迟`）都与工作线程数一致——在闭环中工作线程从不空闲，因此并发度直接决定了后端的负载。
- **单副本在约 256 以上变得不稳定。**在非常高的并发下，单个处理器会压垮网关/EPP 的连接路径（反复出现卡顿和错误）。这正是应当**横向扩展**、而不是把单个副本的并发无限推高的原因（参见[第 4 节](#4-horizontal-scaling)）。

### 如何应用 {#applying-it}

1. 估算（或测量）你的工作负载在路由器处的平均端到端请求延迟 `W`。
2. 设置 `concurrency ≈ ceil(目标吞吐 × W × 1.3)`（1.3 是余量）。
3. 把每个副本的并发度上限设在网关/EPP 能够稳定处理的水平（上述测试中约为 128–256），超出部分通过增加副本解决。
4. **使用饱和度/预算门控时，可以把并发度设得高于这个数值，由门控来限制分发**——但请记住，被门控挡住的工作线程仍会在内存中持有它已拉取的消息，因此不要设得离谱地高。

快速参考（根据参数扫描推导，输出约 256 个 token）：

| 场景 | 目标吞吐 | 大致延迟 | 建议并发度 | 拓扑 |
| :--- | :--- | :--- | :--- | :--- |
| 单块小 GPU（开发） | 约 30 请求/秒 | 约 3–5 秒 | **128** | 1 个副本 |
| 打满 1 块 H100（8B） | 约 40 请求/秒 | 约 5 秒 | **约 192** | 1 个副本 |
| 更大规模的集群 | 线性扩展 | 视工作负载而定 | `吞吐 × W × 1.3` | N 个副本 × ≤256 |

:::note
对于长输出工作负载，`W` 会成比例增长（5 千 token 的补全耗时约为 256 token 的 10–20 倍），所需并发度也随之增长——长输出流水线通常需要数百到一两千的并发，并分摊到多个副本上。
:::

## 3. 容器资源规划 {#3-container-resource-sizing}

Chart 的容器默认值刻意保守——适用于默认的 `concurrency: 64` 和小载荷：

```yaml
resources:
  requests:
    cpu: 100m
    memory: 256Mi
  limits:
    cpu: 500m
    memory: 512Mi
```

请根据真正驱动资源消耗的两个变量来调整这些值：**工作线程并发度**和**每个请求的载荷大小**。

### 内存分配 {#memory-allocation}

内存是最可能需要调优的维度，而且其增长是可预测的：

- **每个请求的缓冲占主导。**每个进行中的工作线程都会在内存中缓冲其请求体和结果载荷。一个粗略的模型：

  ```
  内存 ≈ 基线（约 128 MiB）+（并发度 × 峰值载荷大小 × 缓冲系数 约 2）
  ```

  缓冲系数考虑了同时持有序列化后的请求和响应，以及编解码开销。

- **推高内存的是载荷大小，而不是工作线程数。**对于小载荷（几 KiB），即使并发很高也很便宜：在 `concurrency: 192`、载荷约 16 KiB 时，载荷内存只有 `192 × 16 KiB × 2 ≈ 6 MiB`——默认的 `256Mi` 绰绰有余。大载荷则完全不同：10 万 token 的提示词加 5 千 token 的补全，每个请求约 1 MiB，因此 `concurrency: 256` 需要 `128 MiB + 256 × 1 MiB × 2 ≈ 640 MiB`。**请在载荷较大时增加内存，而不仅仅是在并发较高时。**

- **积压不会堆积在处理器中。**与路由器不同，尚未分发的请求留在消息队列（Redis/Pub/Sub）中，而不是处理器内存中。只有进行中的请求才计入内存占用，这就是内存跟随并发度而不是队列深度变化的原因。

### CPU 分配 {#cpu-allocation}

由于工作线程大部分时间都阻塞在 I/O 上，CPU 消耗很低。它随**分发速率**而不是并发度增长：

- **每次分发的开销**来自请求和结果载荷的 JSON（反）序列化、门控评估以及队列读写。对于典型的智能体载荷，按每 100 次分发/秒约 **0.5–1.0 个 vCPU** 进行预算。载荷越大，序列化开销按比例越高。
- **门控开销。**`prometheus-saturation` 和 `prometheus-budget` 门控会按间隔轮询 Prometheus；开销很小，且与分发速率无关。当许多工作线程共享一个门控时，设置 `ap.prometheusCacheTTL` 可以降低查询频率。`constant` 和 `redis` 门控的 CPU 开销可以忽略。
- **Redis Sorted Set 轮询。**使用 Redis 后端时，`pollIntervalMs`（默认 `1000`）和 `batchSize`（默认 `10`）决定队列读取频率。激进的轮询（间隔短、批次小）会提高空闲时的 CPU 和 Redis 负载；请先调大 `batchSize`，再考虑缩短间隔。

### 规格参考（起点） {#sizing-reference-starting-points}

以下是针对单个副本、按并发度和载荷特征推导出的建议。请把它们当作需要在负载下验证的初始 requests/limits，而不是实测的峰值。

| 工作负载特征 | 并发度 | 载荷（输入/输出） | CPU request | 内存 request | 内存 limit |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 默认 / 轻量 | 64 | 小（≤4k/≤512） | 100m | 256Mi | 512Mi |
| 打满 1 块小 GPU | 128–192 | 小（≤4k/≤512） | 500m | 256Mi | 512Mi |
| 大型智能体 | 256 | 大（100k/1k） | 1 | 1Gi | 2Gi |
| 长输出 | 256 | 大（100k/5k+） | 1 | 2Gi | 4Gi |

注意第二行在并发度提高 2–3 倍的情况下仍然保留了默认内存——小载荷使内存保持平稳；只有大载荷的那几行才需要更多内存。

请把**内存 limit 设置得接近 request**（内存占用受 `并发度 × 载荷` 约束，不会因积压而飙升），并让 CPU limit 相对 request 留出较多余量，以便在不被限流的情况下吸收分发突发。

## 4. 水平扩展 {#4-horizontal-scaling}

一旦单个副本的规格已经比较宽裕，就应优先采用水平扩展，而不是使用单个超大的工作池——这能提升可用性，并分摊队列读取和门控轮询的负载。

- **增加副本以提高进行中总容量**，直到推理资源池能承受的上限：`进行中总数 = 副本数 × 并发度`。超出推理资源池的容量后，门控会关闭阻挡请求，多余的工作线程只会空闲等待。
- **无需协调。**各副本独立地从共享队列中拉取。Redis Sorted Set 和 GCP Pub/Sub 都会把消息分发给多个消费者；Redis Pub/Sub 则是扇出（每个副本都会看到所有消息），因此当负载需要被*分摊*而不是复制时，请使用 Sorted Set 或按消费者订阅的 Pub/Sub 语义。
- **门控在多个副本之间依然有效。**基于 Prometheus 的门控观测的是全局推理服务器饱和度，因此各自独立的副本无需共享状态就能收敛到相同的分发决策。
- **优雅关闭。**处理器在终止时会排空进行中的工作（`drainTimeout`，默认 `2m`）。请确保 Pod 的 `terminationGracePeriodSeconds` 至少等于 `drainTimeout`，以免滚动更新和缩容丢弃进行中的请求。

### Helm 资源覆盖示例 {#helm-resource-override-example}

下面的示例配置值，为大型智能体场景（10 万/1 千载荷）在较高并发下覆盖并发度和容器资源：

```yaml
ap:
  concurrency: 256
  resources:
    requests:
      cpu: "1"
      memory: "1Gi"
    limits:
      cpu: "2"
      memory: "2Gi"
```

```bash
helm install llm-d-async \
  oci://ghcr.io/llm-d/charts/llm-d-async \
  -f guides/batch-serving/asynchronous-processing/${MQ_PROVIDER}/values.yaml \
  -f resource_overrides.yaml \
  --set ap.igwBaseURL=http://${IP}:80 \
  -n ${NAMESPACE} --create-namespace --version ${ASYNC_VERSION}
```
