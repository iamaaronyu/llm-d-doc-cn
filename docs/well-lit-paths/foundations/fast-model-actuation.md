# 快速模型启动

在 Kubernetes 中，一旦某个 Pod 被分配了 GPU，它在整个生命周期内都会独占这些 GPU。因此，扩缩模型服务器意味着创建或销毁整个 Pod，而每个新 Pod 在能够处理第一个请求之前，都要承受完整的**冷启动**——拉取镜像、初始化运行时、加载数 GB 的权重、编译 CUDA graph。在共享 GPU 池上，每次在模型变体之间切换都要重复一次冷启动。

快速模型启动（Fast Model Actuation，FMA）用两种互补的技术缩短 vLLM 的启动时间：**vLLM 休眠/唤醒**，它把已加载模型的张量暂存到主内存，并在几秒内恢复到 GPU——完全跳过模型加载和 CUDA graph 编译；以及一个**启动器（launcher）**进程，它只加载一次 vLLM 的 Python 模块，并按需派生子 vLLM 实例，从而跳过模块导入。两者结合，把模型换入和副本扩容从分钟级的冷启动变成近乎瞬时的操作——且不改变稳态下的服务性能。

:::note
FMA 的价值在于*启动速度*，而不是推理吞吐量。常驻服务器只会增加少量（约 2.5%）的 CPU 内存开销，服务性能与标准部署持平。[工作负载自动扩缩容](workload-autoscaling.md)能力决定*何时*扩缩；FMA 解决的是新容量*多快*能够就绪。
:::

## 架构 {#architecture}

FMA 通过由 FMA 控制器协调的**双 Pod** 设计，绕开了上述独占且贯穿整个生命周期的 GPU 分配：

- **请求方 Pod（server-requesting pods）**通过 Kubernetes 调度器和 kubelet 预留 GPU 资源——保持集群容量统计的准确——但自身并不运行推理。
- **启动器 Pod（launcher pods，即服务提供方）**运行 vLLM，但申请的 GPU 数量为**零**。它们可以通过不计入调度器用量的方式访问所在节点的全部 GPU，FMA 控制器则通过 `CUDA_VISIBLE_DEVICES` 把 vLLM 指向请求方 Pod 预留的特定 GPU。
- **FMA 控制器**负责创建和删除启动器，将请求方绑定到启动器及其中的 vLLM 实例，创建和删除这些 vLLM 实例，并编排休眠/唤醒，使固定的 GPU 池能够承载多个模型变体。

### 启动路径 {#actuation-paths}

需要容量时，控制器会选择一个启动器并采用可用的最快路径：

- **热启动**——唤醒一个已常驻的休眠实例，通过 PCIe 把权重从 CPU 内存搬回 GPU（亚秒级）。
- **温启动**——由已有启动器使用预加载的模块创建一个新的 vLLM 实例（数十秒）。
- **冷启动（使用启动器）**——创建一个新的启动器 Pod，再初始化实例；仍然比不使用 FMA 的冷启动更快，因为后者还要额外承担 Pod 调度和镜像拉取的耗时。

为了控制内存，控制器会限制每个加速器上同时休眠的实例数量（可配置），超出预算时淘汰最近最少使用的实例。
