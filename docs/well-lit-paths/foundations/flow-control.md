# 流量控制

流量控制功能提供智能请求排队。请求排队在以下多种场景中都很有用：

#### 多租户部署 {#multi-tenant-deployments}

与单一工作负载部署相比，运维多租户工作负载还需要额外考虑：

* 某些租户的**优先级更高**（例如付费用户与免费用户）
* 某些请求的 **SLO 不同**（例如批处理与在线请求）
* 某些租户比其他租户更活跃——我们希望它们之间保持**公平**

流量控制为 EPP 引入了智能排队，使运维人员可以把流量动态纳入调度决策。这一能力解决了高低优先级流量混合时的“吵闹邻居”问题；此外，它还确保同等优先级租户之间的公平性，防止任何单个用户耗尽共享资源池、让其他用户“饿死”。

```
单租户                           多租户
  ─────────────                    ────────────

  [A] ──▶ [ GPUs ]               [A] ╲
                                 [B] ──▶ [ GPUs ]
  [B] ──▶ [ GPUs ]               [C] ╱

  [C] ──▶ [ GPUs ]

  每个客户一套部署               一套部署，服务多个客户
```

#### 单一工作负载的“无悔”调度 {#single-workload-no-regret-scheduling}

除了租户间的优先级和公平性之外，流量控制还能在峰值饱和期间暂存请求，从而实现“无悔（no-regret）”调度。EPP 会推迟分发，直到负载回落，而不是把请求提交到某个服务器的队列里卡住，从而确保请求落在当前最合适的资源上。

```
   ┌───┐ 请求  ┌──────────────────────────┐         ┌─────────────┐
   │ A │──────▶│   ┌──────────────────┐   │--------▶│ 服务器 1    │
   └───┘       │   │     请求队列     │   │         │ [█████] 已满│
               │   │ ░░░░░░░░░░░░░░░  │   │         └─────────────┘
   ┌───┐       │   │  [R][R][R][R][R] │   │         ┌─────────────┐
   │ B │──────▶│   └──────────────────┘   │--------▶│ 服务器 2    │
   └───┘       │   ─ 检查负载             │         │ [█████] 已满│
               │   ─ 检测到饱和时         │         └─────────────┘
   ┌───┐       │     将请求排队           │         ┌─────────────┐
   │ C │──────▶│   ─ 容量释放后           │────────▶│ 服务器 3    │
   └───┘       │     放行请求             │         │ [███░░] 60% │
               └──────────────────────────┘         └─────────────┘
```

## 架构 {#architecture}

请求到达代理时，会携带表示租户 ID 和流量优先级的请求头。EPP 利用这些请求头为每个请求分配一个 `FlowKey`（由 `FairnessID` 和 `Priority` 组成的二元组），并为每个 `FlowKey` 维护独立的内存队列。每个 `FlowKey` 会被分配到一个 `PriorityBand`（用于多个租户具有相同优先级的情况）。

然后，在每个调度周期中，EPP 按三个层次遍历队列：

* 优先级——系统总是先服务最高的 `PriorityBand`
* 公平性——在一个 `PriorityBand` 内，由**公平性策略（Fairness Policy）**决定下一个分发哪个流（即租户）
* 排序——在一个流（即租户）内，由**排序策略（Ordering Policy）**决定服务哪个请求（例如 FCFS 或 SLO 感知）

EPP 在后台监控模型服务器是否饱和。如果检测到饱和，请求会排队等待，直到饱和状态消退。

:::warning
**信任边界**：在生产系统中，允许终端用户自行声明其租户 ID 或流量优先级（`premium-traffic`）会成为滥用的入口。在生产环境中，应从外部请求中剥离这些请求头，并由上游受信任的 API 网关、身份提供方或 Envoy AuthZ 过滤器根据 API 密钥注入。
:::
