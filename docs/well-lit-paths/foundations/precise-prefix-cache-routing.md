# 精确前缀缓存路由

对于自己的 GPU 和各存储层中缓存了什么，模型服务器是最准确的信息来源。vLLM、SGLang 和 NVIDIA TensorRT-LLM 会把每一次缓存变化作为事件发布出来；llm-d 订阅这条事件流，构建整个集群中驻留块的近实时视图，并据此为请求打分。前缀亲和性得分会与标准的负载感知打分器组合使用，方式与[优化基线](optimized-baseline.md)路径类似。

KV 事件已成为整个生态暴露准确缓存状态的标准基础——即可复用的推理状态存放在哪里、以及它如何随时间变化。
随着 KV 缓存编排日益复杂、智能体工作负载使前缀越来越长，缓存状态已成为控制面需要观测并据此行动的对象。同一视图可以自然扩展到：

- 跨 GPU HBM、CPU DRAM、本地 NVMe 和共享存储的分层感知缓存追踪；
- 考虑显式提示词缓存放置和动态 KV 卸载的策略；
- 面向集群级 KV 复用的缓存迁移和预取流程；
- 面向智能体模式的高级 KV 保留与淘汰策略；
- 混合注意力模型，其中各层组（全注意力、滑动窗口、线性注意力）独立进行淘汰。

## 架构 {#architecture}

分工很直接：**模型服务器**在每次缓存变化时产生 KV 事件；**llm-d 路由器**消费这些事件，为 Pod 打分以做出更好的路由决策。两端相互解耦——模型服务器和 llm-d 路由器的副本各自独立扩缩。

在 llm-d 路由器内部：

- **索引器（indexer）**消费事件流，为集群中驻留的每个块维护 `block key → pods` 映射。
- **打分器（scorer）**根据输入确定性地推导出块键并查询索引。它返回每个候选 Pod 已缓存的最长连续前缀，并按存储层加权。

事件通过 **Pod 发现**机制，经由 ZMQ 从模型服务器 Pod 流向 llm-d 路由器：每个模型服务器 Pod 绑定自己的 ZMQ socket，每个 llm-d 路由器副本独立订阅每一个 Pod。所有路由器副本最终收敛到相同的索引，因此开箱即可实现双活（active-active）高可用。参考指南默认在一个 Service 后部署两个路由器副本，对于小规模集群也可以缩减到一个。
