# 智能体服务

智能体正在成为生产 LLM 流量的主要形态。一个用户目标会展开成一段很长的*程序*：模型调用与工具执行交替进行——编码智能体、深度研究循环、使用工具的 copilot、多智能体流水线。但推理技术栈仍然是为孤立请求调优的：每次调用都被当作独立请求处理，于是技术栈会重新计算已经见过的上下文，在内存压力下淘汰长期存活的会话，并把热门前缀所在的副本变成热点。

智能体工作负载有三个特性打破了这些以请求为中心的假设：

- **大规模的上下文复用**——推理树的各个分支、工具循环的各轮、智能体群中的各个子任务，共享大部分上下文（系统提示词、工具定义、到目前为止的对话）。
- **程序级目标**——用户关心的是整个程序的完成时间，而不是任何单次调用的延迟；一个卡住的分支可能拖住整个程序。
- **有类型、可预测的生命周期**——持久的系统提示词和工具，与短暂的草稿式思考截然不同；其流程本可被技术栈提前预判，但现在只能被动响应。

这类工作负载的下一个大幅效率提升，不在于对孤立请求做微观优化，而在于让技术栈理解智能体程序的结构，并以**模型状态——目前主要是 KV 缓存——作为协调它的媒介**。

```text
以请求为中心（当前默认）                 程序感知（发展方向）
─────────────────────────────────        ─────────────────────────────
 第 1 轮 ─▶ prefill 160K ─▶ decode        第 1 轮 ─▶ prefill 160K ─▶ decode
 第 2 轮 ─▶ 重新 prefill ─▶ decode        第 2 轮 ─▶ 复用缓存     ─▶ decode
 第 3 轮 ─▶ 重新 prefill ─▶ decode        第 3 轮 ─▶ 复用缓存     ─▶ decode
   （各轮之间 KV 被淘汰）                    （KV 被保留/卸载，恢复时还原）
```

当一个会话恰好落在同一个且有空闲内存的副本上时，单个引擎已经能够跨轮复用缓存；问题出在集群层面——没有跨副本协调，淘汰时不知道哪些块仍被活跃会话需要，也没有请求背后“程序”的概念。

## 典型工作负载 {#canonical-workloads}

llm-d 项目把工作锚定在具体的工作负载形态上，每种形态对技术栈的压力各不相同：

- **长周期循环**（编码智能体、计算机操作）：一个智能体在多轮中反复执行“推理 → 行动 → 观察”。考验跨轮的 KV 持久化、按类型保留以及上下文增长。
- **并行扇出**（best-of-N、树搜索、RL rollout、子智能体）：一个共享上下文派生出许多并发子任务。考验前缀复用、主动复制以及汇合（最慢子任务）延迟。
- **多智能体流水线**（跨 Pod 的多个不同智能体组成的程序，顺序执行或 fork/join）。考验跨资源池的复用与程序身份，以及程序级的统计计量。
- **重推理生成**（回答前进行长时间内部推理）：把工作转移到 decode，并增加每个请求的 KV 占用。

## 部署 {#deploy}

[智能体服务指南](https://github.com/llm-d/llm-d/tree/v0.10.0/guides/agentic-serving)是对应的实操文档。它把 llm-d 现有的成熟路径组合成一套部署栈——用于前缀感知与负载感知路由的[优化基线](../foundations/optimized-baseline.md)、让空闲会话保持驻留的[分层 KV 缓存卸载](../foundations/tiered-prefix-cache.md)、提供精确 KV 状态可见性的[精确前缀缓存路由](../foundations/precise-prefix-cache-routing.md)，以及在负载下保持交互性的 [P/D 分离](../foundations/pd-disaggregation.md)——形成推荐部署方案，按加速器分别实现，并基于一套共享的、贴近真实的智能体工作负载进行基准测试。各层如何对应到工作负载，请参阅该指南。

## 发展方向 {#direction}

[llm-d 项目的智能体北极星文档][northstar]确立了方向：让服务做到*程序感知*而非请求感知，把**会话视为由有类型状态块构成的图**，由控制面基于它进行规划：

- **会话图编排**——把会话建模为由有类型的块（系统提示词、工具目录、对话轮次、推理分支）组成的图；在有外部提示时（例如 Anthropic 的 `cache_control`、OpenAI 的 `prompt_cache_key`）据此构建，否则自动推断。精确的 KV 状态索引是其底层基础。
- **程序感知调度**——基于程序级指标和会拖慢整个循环的关键路径进行调度，而不是追求单请求的公平。这是对 llm-d 路由器的扩展。
- **状态复用与生命周期（“零重算”）**——只要可复用的上下文存在于任何地方（HBM、主机内存、存储），且复用比重新生成更便宜，就不会有节点重新计算它；通过按类型保留，持久上下文被固定，失效分支被丢弃。这建立在 KV 分离、分层卸载以及 Mooncake 等以 KV 为中心的存储之上。
- **主动状态**——当智能体扇出时，上下文会被提前放置到新计算将要落地的位置，而不是按需拉取；放置与调度根据会话图和声明的扇出共同规划。

这一约定分为两层：应用通过它们已在使用的缓存和元数据 API 表达意图，llm-d 在底层完成跨会话、集群范围的工作——提示越好，编排越精准，但即使没有提示，技术栈也能基于推断出的结构正常工作。智能体的控制流和认知决策留在逻辑层（智能体框架、MCP 和 Skills 服务器）；llm-d 提供让它们被高效服务的钩子。

指导性的边界是：**引擎是机制，llm-d 是语义**——语义层位于引擎之上一层，因此这项工作横跨 vLLM、SGLang 及更多引擎。
